Product Requirements Document: Enterprise Multi-Source RAG Engine1. Overview & ObjectivesMost off-the-shelf RAG setups fail in enterprise settings for two main reasons: employees do not trust answers without seeing the source, and naive vector databases happily serve confidential payroll files to an intern if the semantic similarity score is high enough.This engine solves both problems. It provides a reliable question-answering system over messy company documents with strict data access controls, hybrid search, and click-to-verify citations.Core GoalsGrounded truth: Every factual claim must point to an exact document, page number, and text excerpt.Hard tenant and role boundaries: Security happens at the retrieval level, not as an afterthought in prompt instructions.Low hallucination rate: Filter out low-confidence context before generation rather than hoping the LLM admits it doesn't know.Production visibility: Monitor what queries cost, how fast they run, and whether retrieval quality holds up over time.2. 3.1. Ingestion PipelineFile Parsing:PDFs: Extract layout, text, tables, and page numbers using pymupdf or unstructured.Markdown & Notion Exports: Parse headers (#, ##, ###) to preserve hierarchical context.Chunking Strategy:Use parent-child (hierarchical) chunking.Small child chunks (200-300 tokens) are used for embedding generation and precise vector search.Larger parent chunks (800-1200 tokens) are passed to the LLM to give it full surrounding context.Metadata Enrichment:Every chunk is stored with strict metadata:document_id and document_namedepartment and required_role (e.g., ["finance", "exec"])source_type (e.g., pdf, notion, markdown)page_number and char_offset / paragraph_index3.2. Hybrid Retrieval & Re-rankingSparse (BM25): Handles exact matches that vector embeddings often mangle, such as employee IDs, specific financial account codes, product SKUs, and project code names.Dense Vector Search: Handles semantic meaning and conceptual questions using bge-large-en-v1.5 or text-embedding-3-small in pgvector with an HNSW index.Re-ranking: Combine sparse and dense results, then pass the top 20 candidates through a cross-encoder (like bge-reranker-large or Cohere Rerank API). Keep only the top 3 to 5 highest-confidence chunks for the prompt context.3.3. Role-Based Access Control (RBAC)Access rules are applied directly in the database query WHERE clause.If a user has roles: ["marketing"], the vector search query strictly filters: WHERE metadata->>'required_role' = ANY(ARRAY['marketing', 'public']).The LLM never sees chunks the user is not cleared to view, preventing prompt injection attacks designed to exfiltrate private data.3.4. Grounded Citations & Output UIThe generation prompt enforces a strict citation contract: claims must map to numbered citation keys (e.g., [Doc 1, p. 14]).The UI displays:The natural language answer.Inline clickable citation badges.A side drawer that highlights the exact text chunk and page number from the source file when a user clicks a citation.4. Admin Observability & EvaluationTo verify that the system works reliably before and after code changes, track both runtime metrics and evaluation scores:Observability DashboardQuery Latency: P50 and P95 broken down by stage (Retrieval vs. Re-ranking vs. LLM generation). Target: under 2.5 seconds total.Token Cost: Input and output token usage per department and query.Cache Hits: Semantic cache rate for recurring common questions.Evaluation Suite (Ragas / Continuous Eval)Faithfulness: Does the answer rely purely on the retrieved context, or did the model invent facts?Answer Relevance: Does the response directly address the user query?Context Precision & Recall: Did the hybrid search retrieve the actual ground-truth chunks required to answer the question?5.
